Moving big files through a browser, visibly

Three self-contained demos of the same problem: a file too big to POST in one go. Everything runs client-side — the sample 50 MB PDF and Excel workbooks are generated in your tab, and the upload API is simulated in JavaScript — so the whole thing works as a static site on GitHub Pages.

DEMO 1

Chunked upload with a progress bar

Slice a 50 MB file into parts, hash each one, send several in parallel, and watch the bar, throughput and ETA move. Includes retries with backoff, pause/resume, resume after a page reload, and a SHA-256 integrity check at the end.

  • Generate a 50 MB PDF or Excel file on the spot
  • Tune chunk size, parallelism, bandwidth and failure rate
  • Per-chunk status map, live request log
 DEMO 2

Row-by-row import in batches

A workbook with hundreds of thousands of rows is not a file problem, it is a record problem. Parse the sheet in a worker, then post it in batches of 100 / 500 / 1000 rows with a progress bar per batch and a validation report.

  • Build workbooks up to 250k rows in the browser
  • Batch size, parallel batches, retry on failure
  • Rejected rows collected with the reason why
 DEMO 3

Preview Excel and PDF in the tab

Open any of the generated files without downloading them: PDF pages rendered with pdf.js, workbooks rendered as a virtualised grid that stays smooth at 250k rows.

  • Sheet tabs, search, jump-to-row, CSV export
  • PDF paging, zoom, page jump
  • Picks up whatever the other two demos just produced

How the "upload" works without a server

GitHub Pages only serves static files, so the demo ships an in-browser stand-in for the API (assets/js/backend-simulated.js). It implements the same five calls a real service would expose and fakes the network in between — bandwidth, latency, jitter and a failure rate you control:

POST /uploads → { uploadId, received[] } GET /uploads/:id → which parts already landed PUT /uploads/:id/parts/:index → one chunk + its SHA-256 POST /uploads/:id/complete → stitch, verify, finish DELETE /uploads/:id → discard the session

Received parts are written to IndexedDB, which is why a reload mid-upload resumes instead of starting over. The repo also contains a real Node implementation of the same five routes in server/ — start it, paste its URL into demo 1, and the identical client code drives a real upload over the wire.

The sample files are generated, not collected

Nothing here is real data. Both file writers are hand-written and live in this repo:

  • assets/js/pdf-writer.js — emits a real PDF 1.7: catalog, page tree, base-14 fonts, one uncompressed content stream per page. A 50 MB document is ~5,800 landscape ledger pages and takes about a second to build.
  • assets/js/xlsx-writer.js — emits a real OOXML workbook, streaming rows in blocks. It can store the sheet uncompressed, which is the only way to hit a 50 MB target without millions of rows.
  • assets/js/dataset.js — the invented ledger itself: seeded PRNG, fictional names, example-*.test emails, and a deliberate data defect roughly every 150 rows so demo 2 has something to reject.

Smaller pre-built copies are committed in samples/ and load with one click on the preview page, if you would rather not wait for a generator.
